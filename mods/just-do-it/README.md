# Just Do It

> 日本語版は claude-code-mods-ja プロジェクトが翻訳しました。原作者とライセンスは文末を参照してください。原版の README は [README.en.md](README.en.md) を参照してください。

オプトインの継続プラグインです。ネイティブの Python コマンドフックがセッションキャッシュを維持し、モジュールがそのキャッシュを表示して、一時停止、再開、メンテナンス、および助言的な監査を提供します。作業記録は引き続き Linear です。このキャッシュが権限を与えることはありません。

## インストール

```
/plugin install just-do-it@claude-code-mods-ja
```

## 証拠とデリバリー

アクションを求めるリクエストでは、成果（outcome）を DoD、オーナー、実際の Issue 識別子とともに宣言してください。成功した受領記録（receipt）、明示的な検査、型付きのトランスクリプト／ファイルポインタが証拠インデックスを形成します。メタデータの受領記録だけでは成果を証明できません。依存関係のチェックは推移的です。ファイル、証拠、generation が変わった場合は再検査が必要です。

`deliver` は提案された最終テキストそのものと成果 ID を記録します。Stop はそのハッシュを実際のアシスタント最終メッセージと比較し、デリバリーに関係するすべての成果を確認します。欠落、空、不一致、不完全なデリバリーは未解決のままになります。証拠とデリバリーが一致すると `delivered; semantic review pending` となります。

**独立した意味的な完了を証明する経路は現在存在しません。** `audit-record` は実装エージェントから呼び出せるため、その判定、来歴フィールド、さらには `ADEQUAAT` で始まるテキストすらも独立性を確立できません。`/just-do-it audit` はホストが文書化した `model.fork` を 1 回呼び出し、助言目的のテレメトリのみを記録します。HIATEN、ONZEKER、空／エラー、肯定的な助言のいずれの応答でも、意味的な検証は保留のままです。ハッシュはバイトを束ねるものであり、正しさを証明するものではありません。現在の完了経路から accepted/verified のラベルは発行されません。

ブリッジコマンドは `python3 -I <plugin>/hooks/bridge.py ACTION --session SESSION_ID` を使用します。JSON アクションは stdin から読み取ります。現在の generation を使用してください。意図的に楽観的同時実行を使う場合以外は revision を省略してください。

- `contract`: `{"generation":1,"issue":"TEAM-1","outcomes":[{"id":"result","owner":"session","dod":"Required effect","dependencies":[]}]}`。
- `evidence`: `{"generation":1,"id":"result","receipt":"actual-id","pointer":{"type":"transcript","tool":"Bash","tool_use_id":"actual-id","outputHash":"actual-hash"},"inspection":"What the output establishes"}`。ファイルポインタには実際の Read の受領記録と現在のファイルハッシュが必要です。
- `deliver`: `{"generation":1,"text":"Exact final text","outcomes":["result"]}`。
- `reconcile`: `{"generation":2,"items":[{"id":"result","disposition":"retain"}]}`。未解決の `needsReconciliation` 成果は、generation が現在のものであっても 1 バッチですべて処理してください。`contract` でできるのは新しい成果の宣言か、generation を変えずに既存の同一コントラクトを繰り返すことだけです。既存コントラクトの変更には権限のある `reconcile` が必要です。保留リストには調整が必要な自分所有の作業が残ります。`?` で終わる質問には回答できますが、その作業は `next` と保留に表示されたままです。サポートされる disposition は `retain`、`amend`、`add`、`pause`、`cancel`、`supersede` です。各エントリは観測された UserPromptSubmit の generation とプロンプト全体のハッシュに結び付きます。スコープ変更には、保持されたプロンプト先頭 2,000 文字以内の完全一致の引用も必要です。不明な旧形式のプロンプト来歴では調整を承認できません。`amend` には新しい `dod` が必要です。`add` には新しい id、`dod`、`owner`、および `[A-Z][A-Z0-9]+-\d+` に一致するトップレベルの `issue`（`contract` と同じ構文検証）が必要です。または、その検証を通る Issue を持つ既存の成果を指名するトップレベルの `inheritIssueFrom` が必要です。例: `{"generation":2,"inheritIssueFrom":"result","items":[{"id":"result","disposition":"retain"},{"id":"extra","disposition":"add","quote":"add extra","dod":"Extra effect","owner":"session"}]}`。Issue と継承は併用できません。null や任意の識別子は原子的に拒否されます。構文検証では Linear に対する Issue の照合は行いません。`supersede` には、既存または同じバッチで追加された別の `replacement` が必要です。既存の所有権、受領記録、コントラクト、disposition の履歴は保持されます。pause/cancel/supersede は完了を宣言せずに古い成果を停止します。引用は情報源を結び付けるものであり、意味解釈には依然としてレビューが必要です。コントラクトと調整によるキャッシュの編集は、コミット前にトランザクション的に検証されます。
- 任意のコントラクト `criteria`: `[{"id":"bytes","kind":"file-sha256","path":"/absolute/result","sha256":"<64 lowercase hex characters>"}]`。generation と id を指定した `check-outcome` は、各基準を現在の基準ハッシュと generation に対して記録します。Stop は範囲を限定したリンク追跡なしのディレクトリ走査で正確なバイトを再確認します。`{"id":"meaning","kind":"semantic"}` は明示的に保留のままです。コマンドを含む未知の kind は拒否されます。これらのチェックには通常の検査済み証拠も必要であり、バイトの一致が意味的な受け入れを証明することはありません。基準のない成果は証拠のみで意味的には保留のままです。
- `wait`/`release-wait`: 観測された具体的な前提ポインタ、現在の generation、コレクションと id。待機は依存する作業に伝播します。独立した作業は続行されます。解放が権限を与えることはありません。

一時停止、割り込み、承認拒否、ネイティブのループ上限が優先されます。変更のない作業が繰り返されると、診断とトランスクリプトに結び付いた実際の不完全な引き渡しが行われます。再帰的な Claude プロセス、タイマー、デーモン、cron は作成されません。単純な質問に人為的なコントラクトは不要です。停止中の成果は、黙って完了とされるのではなく未解決のままになります。

## ネイティブプロンプトの来歴

ローカルの 2.1.312 型定義は、ネイティブのエンベロープを BaseHookInput に加えて `hook_event_name: UserPromptSubmit`、`prompt: string`、任意の `source: user|sdk|system|loop_wakeup|schedule_wakeup|poll_event`、任意の `session_title` と文書化しています。これらは `source=user` を対話型の入力欄として説明しています。このシリアライズされたフィールドが、任意のブリッジ CLI 呼び出しを認証するものではありません。現在では、`source=user`、`origin=composer`、`authenticated=true` を主張するコールバックも含め、シリアライズされたすべてのプロンプトコールバックが意図、generation、証拠、待機を保持します。`lastPromptSource.authenticated` は常に false です。`reconcile` は、保護されたモジュールから Python への権限転送経路が確立されていないため、旧形式のキャッシュ済みユーザー来歴でも拒否します。

束縛されていないネイティブの `UserPromptSubmit` は、欠落、不明、system、peer、user のいずれの主張であっても、個別の `observationRevision` を進め、`promptBindingPending` を設定します。これは新しいユーザー権限ではなく、観測のバリアです。意図、generation、所有するコントラクト、証拠／履歴、受領記録の検査記録、有効な待機は保持されます。証拠の検査と機械的なチェックは revision に束縛されるため、古い検証は陳腐化し、監査テレメトリには stale の印が付き、古い観測からのデリバリー候補は認識できません。新規の CLI による検査／チェック／デリバリーの記録は現在の observation revision を使用しますが、未解決の束縛を解除することはできません。CLI の権限フラグやリセット操作は公開されておらず、pause/resume でも解除されません。完了の認識を再開するには、サポートされた保護されたホスト経路が必要です。Stop は有効な前提／バックグラウンド待機、通常の会話、ステータス確認では引き続き譲歩できますが、これらの譲歩がデリバリーを主張することはありません。ステータスへの回答では保留中の自分の作業は維持されます。その他の未束縛の作業は、既存のループ上限またはトランスクリプトの引き渡しによって不完全なまま譲歩します。ホストのイベント ID がない同一テキストを含む繰り返しの観測は、それぞれバリアを生成します。既存のイベント ID による重複排除は変更ありません。旧形式のキャッシュは revision 0 で付加的に移行され、新しい束縛の主張は行われません。

モジュールは文書化された `prompt.submit` のみを監視し、エンジン固定の `origin` と `isMeta` をセッションのアトム内に保持します。その観測は、セッション、現在キャッシュされた generation、ローカルシーケンス、正確なテキストの SHA-256、実行中のターン ID（任意）に結び付きます。PromptSubmitInput にホストからメッセージ ID は提供されないため、`observationId` はホストのメッセージ ID ではなくローカルな束縛を明示します。ローカルでは、meta ではない入力欄の origin のみを人間の入力として分類します。権限として CLI にシリアライズされる観測はありません。常に `next(e)` をそのまま呼び出します。型定義によれば、next は下位のモジュールフック、次にネイティブの UserPromptSubmit 設定フックを実行し、プロンプトに入ります。このフックをスキップするポリシーでは観測が残らず、回避のために別のイベントは使用されません。観測やハッシュの失敗でもプロンプトは変更せず転送されます。これはホストローカルの観測であり、ネイティブの認証配線が完了したものではありません。既存の明示的なモジュールの一時停止／再開操作は別個のものです。完全な人間の意図の更新とスコープの調整は、サポートされた保護された引き渡しがなければ Python 経由では引き続き利用できません。

## インシデントの来歴

失敗したツールコールバックが新たに発生するたびに、正確な受領 ID、generation、inputHash、outputHash に結び付いたインシデントが作成されます。同一の重複コールバックは、成功／失敗のコールバック名をまたいで何もしません。矛盾するコールバックのペイロードは元の受領記録を保持し、来歴競合のインシデントを開きます。コマンドや出力のバイトが繰り返されても、個々の呼び出しはそれぞれ独自のインシデントを持ちます。

空の失敗出力やタイムアウトは `effect: unknown` で始まります。書き込みの再試行や免除の要求の前に、ソースを検査して実際の効果を読み戻してください。`waive-incident` には、既存の検査済みローカル証拠、許可された分類、実質的な注記、正確なポインタ、明示的な効果（`not-started`、`confirmed-no-effect`、`effect-confirmed` のいずれか）が必要です。これらは証拠と結び付いたエージェントの主張であり、独立して検証された意味的な事実ではありません。`resolve-incident` にはさらに、所有するプラグインのソース／バックアップのハッシュ、現在の Read の受領記録、検証とロールバックの記録が必要です。

失敗したコールバックの受領記録に結び付いたことのないツール失敗インシデント（`status` の `sourceGaps`）は、検査も免除もできません。`mark-untraceable`（`{generation, ids, note}`。id は一意または 8 文字以上の接頭辞、note は 20 文字以上、すべて成功するか何もしない）は、これらに `provenance.state = untraceable` を記録します。これは注記にすぎません。インシデントは未解決のままで、`waive-incident` と `resolve-incident` は引き続き拒否し、Stop も緩和されません。その後 `status` は、これらを `sourceGaps` ではなく `untraceableIncidents` に表示します。

正確な sourceReceipt を持たない旧形式の未解決ツールインシデントは変更されず、でっち上げた再構築によって免除も解決もできません。その情報源の欠落は、未解決の診断義務です。終了済みの履歴は保持されます。

## メンテナンス

SessionStart は決定的な自プラグインのアダプターを実行します。指定された自スクリプト、マニフェスト、フック設定、モジュール、状態タイプに対する Write／Edit コールバックが成功すると再検査がトリガーされます。これらの正確なパスに対する Read／Write／Edit の失敗コールバックも診断をトリガーします。他の失敗から修復権限が与えられることはありません。ハッシュ／モードのシグネチャには存在しないファイルも含まれ、失敗のフィンガープリントにはコールバック ID が含まれないため、同一の失敗の繰り返しは重複排除されます。30 秒の最小間隔により、作業は次の関連イベントまたはプロンプトまでキューされます。変更のないチェックは 5 分間重複排除されます。タイマーやデーモンはないため、キューされた作業は別のイベントを待ちます。一時停止／割り込みが優先されます。自動診断は、宣言対象へのファイルシステムアクセスごとに明示的な許可リストを確認します。対象は 3 つの自スクリプト、マニフェスト、フック設定、`hooks/register.tsx`、`types/index.d.ts` です。絶対パス、パス走査、不明、不正な形式の宣言は、対象を調査せずに検出結果を出します。シグネチャ、マニフェスト確認、SessionStart の調査、診断、検証、修復の事前確認を含むすべての自動設定読み取りは、既存のディレクトリ fd によるリンク追跡なしのリーダーを使用し、カスタムのシンボリックリンクの祖先と末尾を拒否します。自動スクリプト修復はソースとアーカイブの記述子を固定し、記述子 chmod を使用します。検証時のロールバックも同じ限定リーダーを使用します。手動修復と一般的な証拠ハッシュは、それぞれ独自の動作を維持します。自動診断は PATH を検索しません。より広範な手動診断は、文書化された設定／インストールパス／PATH の範囲を維持します。診断は指定されたプラグインファイルに限定され、修復には `just-do-it` のマニフェストが必要で、指定された自スクリプトに対して所有者の実行ビットを最大 3 回だけ修復します。各修復は `apply_fix`、バックアップ／ハッシュの検証、競合を考慮したロールバックを再利用します。HOME／config／secret のスキャンは自動では実行されません。状態のアーカイブは、経過時間だけでは成果の完了を証明できないため、手動のメンテナンス操作のままです。

`/just-do-it maintain` は、指定されたプラグインファイルと、既存の設定およびインストール済みプラグイン記録のうちフック／インストールパスの部分を読み取ります。`maintain record` は high／medium の検出結果を記録します。`maintain fix` は既存の明示的に安全な自プラグイン修復のみを適用します。未知のオプションは読み取り専用のままです。外部の設定／フック／プラグインの検出結果は提案にすぎません。ガード、権限、ルーティング、他のプラグイン、認証、認証情報が変更されることはありません。

外部の診断アダプターは保留のままです。インストール済みの `hook-doctor` スキルは、読み取り専用の `node <hook-doctor>/bin/doctor.mjs <project> --json` 診断を文書化しています（ネットワークアクセスや書き込みなし）。ただし、ユーザー設定と参照先スクリプトも読み取ります。自動的には呼び出されません。ブリッジの閉じたローカル専用のインポート／プロセス契約ではサブプロセスの経路が許可されず、外部アダプターには別途境界を定めたホスト側の連携が必要です。その検出結果から広範な修復権限を推論してはいけません。Python フックの起動前に発生する失敗、Bash による設定の書き込み、正確に指定されたファイル以外の変更、後に対応するイベントがない外部編集は、自動的には観測されません。`maintenance.coverage` フィールドが、この限定されたアダプターの範囲を明示します。所有権はマニフェストとファイルの所有者によりローカルで確認されます。これはフリートのリースや排他書き込みの証明ではありません。インストールとメンテナンスは、他のプラグインの書き込みが停止している状態で実行してください。

## パネル

ペインはセッション開始、ターン完了、コマンド、手動更新時に、権限のあるブリッジの状態を読み取ります。個々の成果の基準／証拠の数、フェーズ、次のアクション、最後に成功した更新を表示します。読み取りに失敗すると、保持しているスナップショットに古い旨を明示します。ポーリングは行いません。外部で行われた変更は、次の更新時に表示されます。件数がカバレッジや完了を示すことはありません。

## インストーラーの安全性

`../install.sh install|update|uninstall` は、ネイティブのユーザースコープのプラグイン CLI を使用します。`.ops-jdi-owner.json` のない既存のマーケットプレースは拒否されます。旧形式のインストールに対してマーカーをでっち上げないでください。不明なファイル／ランタイムは、衝突チェック、非公開のバックアップ、競合を考慮したロールバックとともに保持されます。`rollback <backup>` には、対応する所有するインストールが必要です。この候補に対して実際のインストーラーは実行されていません。

`install.py` は読み取り専用の `runtime_manifest(root)` と `compare_runtime(source,target)` を公開します。ランタイムハッシュマップに入るのは、明示的に指定されたマニフェスト、フック、ブリッジ／モジュール、プラグインの状態タイプだけです。ホストが生成した宣言、テスト、ランタイム、不明なファイルは対象外です。比較によって所有権を取得したり同期を承認したりすることはありません。既存のインストーラーの変更動作は別個のものです。

## 任意のフリート検査

マニフェストは任意の `userConfig.fleetConfigPath`（ファイル、既定値は空）を宣言します。ネイティブモジュールの一覧では、コアモジュールの後に `fleet-entry.ts` が追加され、すべてのコマンドフックは維持されます。パスが存在しないか空の場合、フリート検査は無効です。明示的な絶対パスの非公開設定が必要であり、さらに 0 でない永続的な judge 許容値を設定した場合にのみ、セッション所有の 60 秒タイマーが開始されます。有効な検査はホストモデルを呼び出す場合があります。このオフライン連携ではモデル呼び出しは行われていません。セッション終了と無効／無効化された設定はタイマーをキャンセルします。ソースの境界と設定フィールドについては [the fleet contract](docs/fleet-guard.md) を参照してください。

フリートの判定は助言にすぎません。キューされた助言は、実行でも、効果の受領でも、承認でも、完了でもありません。ネイティブ側のソース安全性の欠落により、現在は助言の送信が行えません。保護されたホストからネイティブへの origin 転送は未解決のままです。ローカルの人間のトランスクリプト観測は、`promptBindingPending` を解除せず、ブリッジの調整を承認せず、ブリッジによる独立した受け入れを確立することもありません。普遍的な完了保証や、実行時の受け入れを主張するものはありません。

ランタイムハッシュマップには、コアファイルとともに `fleet_guard.py`、`fleet.ts`、`fleet-source.py`、`fleet-runtime.ts`、`fleet-entry.ts` が含まれます。既存のインストーラーのバックアップ、衝突、所有権、ランタイム、不明ファイル保持の規則は引き続き適用されます。所有権のない現在のマーケットプレースは拒否する必要があります。

```
claude plugin validate <plugin>
python3 -I <plugin>/repair_fixture.py
```

トランスクリプトメッセージの走査には、POSIX のディレクトリ fd による `open`／`stat`、リンク追跡なしの `stat`、`O_DIRECTORY`、`O_NOFOLLOW`、`O_NONBLOCK` が必要です。対応していないプラットフォームでは、引き渡し保留で fail closed します。すべてのディレクトリは保持している親記述子を基準に、リンクを追わずに開かれます。受け入れ前に、葉の所有者／種別、前後の同一性、ディレクトリの辺が確認されます。macOS では、正確にルート所有のシステムリンク `/var -> private/var`、`/tmp -> private/tmp`、`/etc -> private/etc` のみを展開して再確認し、その `/private/...` の対象も同じリンク追跡なしの走査を受けます。カスタムのシンボリックリンクの祖先と葉は拒否されます。走査中に観測された並行変更は保留のままです。これは観測時点の確認であり、ファイルシステムのロックや意味的な認証ではありません。上限は合計 128 MB、レコードごとに 1 MB、5 秒のままです。一般的なファイル証拠には別途 16 MB の上限があります。

テストは一時フィクスチャとホストのモックを使用し、実際にインストールされたセッションではありません。ローカルの Stop スクリプトにはネットワーク／モデル／サブプロセスの経路はありません。タイミングの確認は請求ではなくローカルのレイテンシを測ります。明示的なモデル呼び出しは `/just-do-it audit` のみで、通常の Stop は行いません。これらのコマンドが有料の証明を承認することはありません。

`smoke.py` は `--run-paid-smoke` と具体的な `--max-budget-usd` の両方を必要とします。明示的なオプトインがなければ何も消費しません。その構造的な想定は、意味的なレビュー保留付きのデリバリーであり、独立した受け入れではありません。新たに承認された予算なしに有料スモークを実行しないでください。

未実装：真正な独立した意味レビューの来歴、正確なファイルバイトを超える DoD ごとの完全な型付き意味検証、外部のメンテナンスアダプターとホストのフック起動失敗の観測、実際のパネル／ネイティブセッション／インストールの受け入れ、有料のランタイムコストの証明。キャッシュのトランザクションはファイルシステムの修復を原子的にするものではなく、既存の修復ロールバックが別途処理します。プロンプトハッシュは観測されたコールバックの連鎖を示すものであり、ホストが認証したユーザー ID を示すものではありません。ソースの完全性と実際のユーザーの意図は、依然としてレビュー義務です。オフラインテストではこれらの要件は満たされません。最終候補には別途の独立レビューが必要です。
